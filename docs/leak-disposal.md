# 渗漏返工判定收拢说明

渗漏程度、处置方式、返工判定曾经各写一遍（列表一遍、动作一遍、另存排序一遍），三处结论互相
冲突。现已收拢成一份共用实现：`frontend/src/domain/leak-disposal.ts`。列表、动作流转、
另存清单、详情面板、值班台账要情全部调这一份，返工与完工的分界只保留一份判定。

## 判定口径（唯一一份）

- **渗漏程度**：按关键词归一化为 轻微(1) / 一般(2) / 严重(3) / 涌水(4)；空值或无法识别
  一律按「一般」兜底，并在判定说明里写明。
- **处置方式**：归一化为 注浆堵漏、结构加固（根治性）与 引排导流、表面封堵（临时性）；
  空值记「待补录」，无法识别的按临时性兜底（宁严勿宽），同样写进判定说明。
- **返工分界（唯一）**：程度严重及以上（level ≥ 3）且处置方式不是根治性 → 需返工；
  其余 → 免返工。`确认完工` 被这份判定拦截：判定需返工的单子不能确认完工；
  `要求返工` 可以人工覆盖免返工结论，覆盖原因写回判定说明。
- **处置编号缺失**：按待补录处理，判定说明里注明，所有动作拦截，补录编号后再参与判定。

判定结论（处置等级、处置方式认定、返工判定、判定说明、判定基准日）落在行记录上，
与状态流转在同一个事务里写入——记录上不会残留上一轮的处置等级。这几个字段不在模块
字段清单里，**另存清单的列与字段不变**，只按记录上同一份判定定先后（需返工 → 待补录 →
其余按发现日期升序）。

## 两版取值取舍（已定）

**待办（pending）的终态取值**：通用模块约定「状态列表最后一个为终态」，渗漏模块的状态
列表是 待处置/处置中/已完工/需返工，按通用约定「需返工」才是终态——这会让已完工的单子
仍算待办、需返工的反而清零，待办清单与值班台账必然对不上。**取舍：渗漏模块以「已完工」
为唯一终态**，待处置/处置中/需返工都算待办。理由：需返工是要继续干的活，不是终点；
只有这样，运营概览的待办数与值班台账的渗漏要情才能条数一致、同步变化。

## 存量迁移规则（幂等，每次落库前自动执行）

- 已判定过的处置单**不改等级**；没判过的按**发现日期**回填判定（判定基准日 = 发现日期），
  历史处置单的状态与待办标记一律不动，保留原判。
- **早年没有处置方式的**：按渗漏程度推导补上——严重及以上 → 注浆堵漏，其余 → 表面封堵，
  判定说明标注「存量回填」。取舍理由：显式留空会让老单永远卡在待补录、无法流转；
  一刀切按临时性会把历史完工单全判成需返工，推翻原判。按程度推导既让老单参与统一判定，
  又不改变它们已有的结论。
- 值班台账按**交接班次**迁移：交接编号缺失的按「值班日期+班次+序号」补齐，其余缺项
  **显式留空**（空字符串），不猜内容。

## 重复上报与导入

- 同一张处置单再次导入**不会多出一条记录**：有处置编号按编号归并，缺编号按
  「渗漏点位+发现日期」兜底。
- 重复上报**只认第一次的内容**，后续差异逐字段对比后只记进备注
  （`重复上报差异（日期）：字段「旧→新」`），原记录不覆盖。
- 导入整体走一个事务：任何一行字段数对不上、或落库校验不过，**整笔退回**，一条都不写。

## 一致性保证

- 所有写入统一走 `local-store.ts` 的 `commit`：迁移 → 整体校验 → 一次性换快照并持久化；
  任何一步失败缓存与 localStorage 都不动。提交成功后所有读取看到的是同一份新快照，
  前后两次读到的必须是同一份数据。
- 渗漏列表的统计卡片、状态分布、值班台账的「渗漏处置要情」、运营概览的待办清单，
  都从同一份行数据经同一个 `leakSummary` 算出，两处条数一致、同步变化。
