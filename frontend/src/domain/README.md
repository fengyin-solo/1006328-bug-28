# 渗漏水处置 / 值班台账 —— 判定口径与取舍说明

本目录是全平台**唯一**的业务判定实现。页面（列表、详情面板）、动作流转、另存归档、
导入去重、值班台账联动都只读这里的纯函数，不再各写一遍。

- `leak.ts` —— 渗漏程度 → 处置方式 → 返工 / 完工判定，归档排序与导入去重
- `duty.ts` —— 值班班次归一、渗漏待办按交接班次归集

## 1. 一处判定，三处共用

渗漏返工原先在三个地方各算一遍（列表按渗漏程度算、「要求返工」动作再算、
另存时为定先后又算），口径互相冲突，同一张单列表显示需返工、另存后却成已完工。

收拢后：

| 入口 | 读取方式 |
| --- | --- |
| 处置清单列表 | `projectLeakRow(row)`，按唯一判定投影，列表预判返工与动作判定同源 |
| 详情面板 | `getLeakEntry(id)` → 同一个投影，不另算 |
| 另存清单 / 导出 | `buildLeakArchive(rows)` 只搬运判定为「已完工」的同一结论，按发现日期排序 |
| 「确认完工 / 要求返工」动作 | `resolveLeakVerdict(row).canComplete / rework`，只按这份结论落锁 |
| 导入 | `parseLeakImport` 归一程度 / 方式，落库后仍由同一份判定出结论 |

## 2. 返工与完工的分界（只此一份）

`reworkRequired(degree, method)`：

- **严重渗漏必须采用注浆封堵**；严重渗漏实际工艺是引排水处理 / 紧急加固的，一律需返工；
- 中度渗漏、轻微渗漏只要处置方式已落实，即满足完工条件；
- 渗漏程度未核定时不臆断返工，转人工核定，不能确认完工。

「确认完工」若撞上返工分界，不允许完工，自动落「需返工」并写判定锁；动作页与列表
显示的结论永远一致。

## 3. 已经判定过的处置单：不改等级

历史单据（状态为已完工 / 需返工）在迁移和每次动作落库时写 `判定锁定 / 判定结论`。
`resolveLeakVerdict` 对锁定单据**原样返回历史结论**：

- 早年严重渗漏用紧急加固就完工的单子，虽然按现行口径落在返工分界上，**仍保留已完工**，
  只在备注里注明口径差异；
- 需返工的单据必须走「重新派出处置」，重新派出时清掉旧锁，按新一轮现场工艺重新判定，
  上一轮处置等级不残留在记录上（修复合并前「并完之后结论对不上」的问题）。

## 4. 另存清单的列与字段不变

另存清单与原清单导出表头完全一致：`编号 + 8 列（处置编号、渗漏点位、渗漏程度、处置方式、
处置班组、发现日期、完工日期、处置状态）+ 当前状态`。归档只收录已完工处置单，
先后顺序按**发现日期升序**（同日按 id），发现日期缺失的排最后，不做删除。

归档分片 `leakArchive` 不手写：任何渗漏数据提交（`commitEntries`）时都由
`buildLeakArchive` 按同一口径重建。返工的单子在同一笔提交里自动移出归档，
待办清单同步变化。

## 5. 处置编号缺失：按待补录处理

- 编号为空 / `（待补录）` 的单据状态统一为「待补录」，不进入处置流程，不能派出、不能完工；
- 列表与详情显示 `（待补录）` 并给出说明，「补录编号」后转入「待处置」；
- 导入时缺编号允许进入（真实场景常是现场先报点），但同样落待补录。

## 6. 重复导入 / 重复上报

去重身份（`leakIdentityKey`）：有处置编号按编号；**编号缺失按「渗漏点位 + 发现日期」**
认定同一个渗漏点。

- 命中已存在单据：**只认第一次上报的内容**，后续上报的任何字段差异不覆盖原值，
  按「第 N 次重复上报（日期）以首次上报为准；差异：X 旧→新（未采纳）」追加备注；
- 同一批导入文件内部出现两个相同身份：无法判断先后，**整笔退回**，要求人工合并。

## 7. 整笔提交，落库不完整就退回

`local-store.ts` 的 `commitEntries` 顺序固定：

1. 校验（编号必须为数字、同模块不允许重复编号）；
2. 重建归档分片；
3. **先写 localStorage**（抛错时内存缓存保持旧值不动）；
4. 写成功后才切换内存缓存。

任何一步失败都保持旧数据，前后两次读到的是同一份数据。多个标签页同时开时，
监听 `storage` 事件作废旧缓存，下一次读取以磁盘为准。

## 8. 存量数据迁移（v1 → v2）

旧 localStorage 数据在首次读取时整库迁移并一次性写回（带版本号 `version: 2`）。

### 渗漏处置单

1. 渗漏程度 / 处置方式过统一别名表（如「涌水、重度」→ 严重渗漏；「灌浆」→ 注浆封堵）；
2. **处置编号缺失 → 待补录**；
3. 缺项（点位、班组等）清空占位演示值，显式留空；
4. 发现日期不合法的显式留空并备注；
5. **早年没有处置方式的历史已完工单：按渗漏程度回填标准工艺**
   （轻微→引排水处理，中度及以上→注浆封堵），历史结论保留，备注写明回填原因。
   取舍理由：完工单据必须有可核查工艺，按发现日期当时的标准工艺回填比留空更可追溯，
   且不动判定等级，不影响历史责任认定；
6. 已完工 / 需返工写判定锁定，保留原判（含与现行口径不一致的老单）；
7. 完工日期与流程状态冲突时，**以流程状态为准**清空日期并备注
   （取舍理由：日期可能是补录误填，流程状态是实际操作留痕，可信度更高；原值在备注保留）。

仓库生成的占位演示值（如「渗漏水处置样例2」）不属于真实数据：程度按点位序号
启发式回填轻 / 中 / 重并备注「请现场核定」；真实但未识别的取值**保持原值**待核定，
不强行归类。

### 值班台账

1. **按交接班次迁移**：班次别名（日班/早班/白班/day…）归一为 `白班 08:00-20:00`、
   `夜班 20:00-次日08:00` 两套全称；
2. 班次认不出来的**显式留空待补**，不擅自派班（取舍理由：错派班会污染责任交接记录，
   留空可查，乱派不可查）；占位演示数据按序号轮排白 / 夜班并备注请核实；
3. 其他缺项（交接事项、交接人员等）要么按别名补齐，要么显式写 `（留空）`；
4. 值班日期不合法显式留空，`pending / abnormal` 按状态重算。

## 9. 两处条数一致：值班台账联动

- 渗漏页「待办清单」与值班页「渗漏待办按交接班次归集」都调用
  `groupLeakTodosByShift(leakRows, dutyRows)` 这一个函数，合计条数恒等；
- 待办 = 未完工单据（待补录 / 待处置 / 处置中 / 需返工），已完工（含归档）不进待办；
- 按发现日期匹配在册班次；当天白 / 夜班都在册时，无时间信息默认归白班；
  匹配不到的显式归入「未排入班次」，不丢弃不乱派；
- 归档 / 返工导致待办变化时，动作走的是同一笔 `commitEntries`，两页重新加载即同步。

## 10. 两版取值冲突的取舍汇总

| 冲突点 | 保留版本 | 理由 |
| --- | --- | --- |
| 流程状态 vs 完工日期 | 流程状态 | 流程状态是实际操作留痕；日期可补录误填，清空并在备注留痕 |
| 重复上报首报 vs 后续差异 | 第一次上报 | 避免后报覆盖先核的现场结论；差异进备注可追溯 |
| 老单旧工艺 vs 现行返工口径 | 历史原判 | 已判定单据不溯及既往，责任认定需要稳定结论 |
| 早年缺处置方式 | 按程度回填标准工艺 | 完工单据需可核查工艺；回填可追溯且不改判定 |
| 无法识别的班次 | 显式留空 | 错派班污染交接责任，留空可查 |
